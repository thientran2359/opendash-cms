## Phạm vi và điều kiện áp dụng

Đặc tả G2 cho P10, P12–P15, P17–P19 trong G0 M3 phương án A. Giữ [ADR-0004](ADR-0004-m3-post-page-publication-boundary.md), [Core Foundation](../contracts/CORE_FOUNDATION.md) và [Plugin ABI](../contracts/PLUGIN_ABI.md). M3 dùng homepage một block hiện có. Taxonomy, Builder AST, template composition, plugin CPT/field bridge, video, media delete/reconcile và backup engine vẫn theo milestone đã duyệt. Quyết định sản phẩm P14 về homepage do chủ dự án xác nhận ngày 2026-11-11. Phần kỹ thuật cần quyết định theo [ADR-0003](ADR-0003-agent-consensus-governance.md) và tích hợp tài liệu trước khi chuyển sang `AGREED`. Forge/Harbor thực hiện G3 theo [ADR-0005](ADR-0005-m3-harbor-forge-autonomous-delivery.md).

## Hợp đồng dùng chung

- HTTP đi qua router và guard hiện có. Thiếu session hoặc session đã bị thu hồi trả 401. Role không đủ, Origin không hợp lệ hoặc thiếu/sai CSRF trả 403 theo guard hiện hành. Invalid payload trả 400, ID hợp lệ nhưng không tồn tại trả 404, xung đột domain trả 409. Mutation có CAS dùng `If-Match: "vN"`. Thiếu trả 428, sai định dạng trả 400, version cũ trả 412. Lỗi storage ngoài dự kiến trả 500 qua `ApiError` với thông báo đã lọc. Lỗi SQLite writer bận sau timeout trả 503 cho mutation mới và giữ draft trong UI.
- Response riêng tư mới dùng `Cache-Control: no-store`. JSON dùng tên field snake_case và kiểu số nguyên an toàn với client hiện có. UI dùng client session/CSRF hiện hành, giữ input khi 401/412 hoặc lỗi lưu, có đường tải lại dữ liệu và retry chủ động. Màn mới có label, keyboard focus, trạng thái loading/empty/error phân biệt và không overflow tại 390 px. Màn Admin-only phải được bảo vệ ở cả router UI lẫn backend.
- Dùng migration tiến tới, đánh số tập trung theo `main`. Giữ nguyên migrations 0001–0008 và preflight collision trước 0008. Mọi truy vấn SQL thuộc `storage`. Mọi fixture rollback chạy trên site copy với snapshot DB và assets nhất quán. Tích hợp code/rollback dùng binary tương ứng với schema của snapshot.

## P12 · Users (FND-02/FND-05, Full-Track)

Giữ bảng `users` và `sessions`. Thêm `users.version INTEGER NOT NULL DEFAULT 1 CHECK(version >= 1)`. Mọi thay đổi username, role hoặc password tăng version. Identity là `id` số nguyên dương. Giữ quy tắc username/password của `auth` và Argon2 của baseline. User summary chỉ gồm `{id,username,role,version}`.

| Endpoint Admin | Request / response |
| --- | --- |
| `GET /api/admin/users?limit&offset` | Mặc định 50/0, limit 1–100, offset không âm. Sắp xếp `id ASC`, trả `{items,total}` từ một snapshot. |
| `POST /api/admin/users` | `{username,password,role?}`, mặc định `editor` để giữ client cũ. Trả 201 và summary. |
| `PATCH /api/admin/users/{id}` | `{username?,role?}`, ít nhất một field. Trả summary và ETag mới, hoặc summary/version hiện hành nếu giá trị không đổi. |
| `POST /api/admin/users/{id}/password` | `{password}`, trả summary và ETag mới. Đây là reset do Admin thao tác trực tiếp. |
| `DELETE /api/admin/users/{id}` | Xóa tài khoản và session, trả 204. Áp dụng cùng ràng buộc Admin cuối. |

Ba mutation theo ID dùng CAS. Duplicate username hoặc xóa/hạ quyền Admin cuối trả 409. Hash trước khi giữ write lock. Sau khi bắt đầu transaction có write reservation, kiểm tra lại session và role actor, lấy target/version và số Admin, áp dụng mutation và xóa toàn bộ session target trong cùng transaction. Thay đổi chính mình buộc đăng nhập lại sau phản hồi thành công. Login xác minh password ngoài transaction rồi insert session có điều kiện `id/version` vẫn khớp. Nếu reset thắng cuộc đua, login cũ thất bại hoặc session vừa tạo bị revoke trong transaction reset. Giữ bootstrap hiện tại và FK `ON DELETE CASCADE`.

Chọn transaction ở storage vì đếm Admin trong handler để hở khoảng giữa check và write. Dùng fixture hai Admin, hai session, thử hai thao tác hạ quyền/xóa đồng thời và race login/reset có đồng bộ. Sau thử nghiệm còn ít nhất một Admin đăng nhập được, phiên bị revoke trả 401, mật khẩu mới hoạt động, bootstrap và client tạo Editor cũ vẫn chạy. Fixture restart kiểm role/version, session và password hash. Password, token và hash không xuất hiện trong DTO hoặc log.

## P13 · General Settings (SITE-01, Full-Track)

Thêm `site_general_settings` singleton với `id=1`, `site_title`, `tagline`, `timezone`, `version>=1`. Migration khởi tạo `{site_title:"OpenDash",tagline:"",timezone:"UTC",version:1}` cho cả fresh và upgrade. Giữ typed singleton vì các field có chủ sở hữu và validation riêng. Kho KV tổng quát sẽ mở thêm bề mặt settings của theme/plugin ngoài P13. Title trim, 1–120 Unicode scalar values. Tagline trim, 0–240. Cả hai từ chối control characters. Timezone match chính xác danh sách `TZ` trong `zone1970.tab` từ **IANA tzdb 2026f**, cộng `UTC`. Bundle danh sách theo build, ghi provenance và version. Giữ UTC trong SQLite và session timestamps. Nếu dữ liệu cũ chứa một timezone hợp lệ tại bản trước mà catalog mới loại bỏ, GET giữ nguyên giá trị và người dùng có thể lưu lại nguyên giá trị hoặc chuyển sang mục hiện hành. [IANA tzdb 2026f](https://www.iana.org/time-zones/releases/2026f)

`GET /api/admin/settings/general` trả `{site_title,tagline,timezone,version}` và ETag. `GET /api/admin/settings/timezones` trả `{version:"2026f",items:[...]}` sắp xếp theo ID để UI chọn từ danh mục server. `PUT /api/admin/settings/general` nhận đủ ba field cấu hình và CAS, trả object và ETag sau commit. Scope Admin-only. Tên site và tagline hiển thị đã escape trong khung mặc định của trang danh sách/chi tiết nội dung. Theme custom chỉ nhận hai chuỗi qua context `site.title`/`site.tagline`, giữ template cũ hoạt động khi không dùng context này. Homepage tiếp tục theo P14. Màn Settings có ví dụ thời gian theo zone đã chọn, format bằng `Intl.DateTimeFormat` với timezone explicit và thông báo nếu browser thiếu zone. UTC vẫn là giá trị hiển thị dự phòng, không ghi đè cấu hình đã lưu.

Acceptance gồm fresh/upgrade defaults, giữ giá trị sau restart, hai tab ghi cùng ETag, Editor 403, payload sai và output escaping trên public route. Kiểm `Asia/Ho_Chi_Minh` và `America/New_York` bằng timestamp cố định có offset khác nhau giữa mùa hè và mùa đông.

## P10 · Dashboard (FND-05/CNT-04, Full-Track)

`GET /api/admin/dashboard` dùng `require_session` cho Admin và Editor. Response `{post:{draft,published},page:{draft,published}}`, bốn trường là số nguyên không âm và trả 0 nếu chưa có bài. Storage thực hiện một truy vấn aggregate cho hai built-in type theo policy xem danh sách của ADR-0004, hiện cả Admin và Editor thấy cùng tập Post/Page. Bỏ qua CPT tùy chỉnh. Không đưa IDs, username, logs hoặc diagnostic nội bộ vào payload. Dùng aggregate server-side để tránh sai số do pagination hoặc hai snapshot khác nhau. Lấy dữ liệu mỗi khi vào Dashboard, có nút thử lại khi lỗi và giữ shortcut hiện có theo role. Dùng fixture ít nhất một draft và published trên cả hai type, kiểm số trước/sau publish/unpublish và zero state, guest 401, Editor quyền đúng, UI khi request thất bại.

## P14 · Themes (THM-01/FND-05, Full-Track)

**Hành vi sản phẩm đã chốt:** Kích hoạt theme đổi giao diện homepage theo theme active. Nội dung vẫn lấy từ homepage đã lưu trong Admin. Block tương thích render theo theme active. Block thiếu hỗ trợ bị bỏ qua trên website và vẫn giữ ID, giá trị và vị trí đã lưu để hiện lại khi đổi về theme tương thích.

- Theme M3 định danh bằng ID block trong `block.json` của gói đã cài. Dùng `theme_blocks` hiện có. Thêm bảng singleton `site_active_theme(id,block_id,version)` với FK đến `theme_blocks`, khởi tạo `block_id=NULL`, `version=1`. `NULL` duy trì hành vi legacy trên site chưa chủ động kích hoạt. Thêm cột nullable lưu ID tương thích của gói. Lưu active pointer và tăng version bằng CAS một lần trong storage. Install/activate chỉ ghi vào bảng do THM-01 sở hữu. `home_page` giữ nguyên khi kích hoạt, kể cả lúc block không tương thích. Trả ngay giao diện theo active theme sau commit, archive/single dùng template active và built-in fallback khi thiếu template.
- Giữ định dạng ZIP hiện có. Chấp nhận thêm đúng một file gốc tùy chọn `homepage-compat.json` có schema `{"version":1,"accepts":"owner/block"}`. Dùng kiểm tra namespaced block ID hiện có, một alias tối đa. Alias trỏ tới block đã cài, khác ID của gói mới. Tập field key phải khớp chính xác với `block.json` của block gốc. Từ chối alias chưa cài, tự tham chiếu, schema/version sai hoặc field key lệch trước khi ghi. Registry giữ owner thật của cả hai block. Binding render chỉ chọn `block.html` của theme active và truyền values đã lưu theo field keys. Không lookup HTML từ theme cũ khi active không hỗ trợ. Giữ tổng quota ZIP 64 KiB hiện có, flat allowlist, unique filenames, template validation và sandbox/CSP. So với đoán theo tên block hoặc dùng lại template cũ, khai báo explicit giúp kiểm đúng hợp đồng field và hành vi ẩn block.
- Resolver dùng chung cho `/`, preview và response Save. Trùng ID với active hoặc alias hợp lệ thì render bằng template active. Thiếu hỗ trợ thì trả trang HTML an toàn với vùng nội dung rỗng và HTTP 200. Giữ response HTML của `POST /preview` và `POST /save`. Hai response Admin này có `Cache-Control: no-store` và header `X-OpenDash-Block-Visibility: rendered|unsupported` để Builder hiện cảnh báo bên ngoài iframe. Public `/` không trả diagnostic này. Save kiểm theo schema gốc và lưu đúng block người dùng chọn. Preview dùng draft chưa lưu, không ghi DB. Public đọc `home_page` và active theme trong cùng snapshot. Save chốt dữ liệu và chọn active theme cho response trước khi dispatch hook hiện có sau commit.
- `GET /api/admin/themes` trả `{items,active_id,version,homepage_compatible}` và ETag. `items` gồm `{id,compatible_block_id}`. `homepage_compatible` là `null` khi chưa có homepage hoặc chưa kích hoạt theme explicit. `POST /api/admin/themes` nhận ZIP, tái sử dụng use case của `/theme`, trả 201 và item. Giữ response `/theme` cho client cũ. `PUT /api/admin/themes/active` nhận `{id}`, dùng CAS và trả cùng representation như GET. Cài trùng trả 409, target thiếu 404, ZIP/schema lỗi 400. Rollback bằng cách kích hoạt lại theme trước, hoặc dùng site snapshot khi rollback binary/schema.
- Ca A→B: B khai báo hỗ trợ block A, `/` hiển thị dữ liệu đã lưu theo markup của B. Ca A→C: C thiếu hỗ trợ, `/` trả 200 và ẩn block, Builder vẫn giữ field values. C→A khôi phục hiển thị cả sau restart. Kiểm preview draft chưa lưu, Save, hai activation cùng ETag, ZIP lỗi không có partial state, và so snapshot `home_page`, CPT, Post/Page, media refs trước/sau đổi theme. Giữ URL, publication ACL và CSP hiện hành.

## P15 · Plugins (PLG-01/FND-05, Fast-Track)

Dùng nguyên các endpoint list/install/enable/disable, permission manifest, ABI và worker hiện có. Màn Plugins trình bày quyền, version, trạng thái và lỗi đã lọc. Với upload, bước xác nhận trước submit nói rõ gói cùng ID được thay và bật lại theo API hiện hành. Với enable, hiện quyền mà server đã trả về cho gói đang cài. Sau thao tác reload summary từ server, khóa nút thao tác đang gửi và cung cấp đường retry chủ động nếu thất bại. Chọn giữ hành vi replace-and-enable đã có để tránh thay hợp đồng legacy trong task UI. Nếu phát hiện quyền sai, lỗi không thể disable, hoặc yêu cầu thay quy tắc replace/enable, tách Full-Track và dừng phát hành phần bị ảnh hưởng cho đến khi có giải pháp. Không thay logic worker hoặc ABI trong P15.

Acceptance dùng fixture plugin hiện có cho fresh install, cùng ID thay gói, enable/disable, restart và lỗi worker. Editor gọi API trực tiếp trả 403. ZIP sai không đổi plugin state. Worker timeout vẫn cho Admin mở trang và disable. Disabled plugin không nhận invocation mới theo ABI hiện hành, plugin KV và dữ liệu nội dung còn qua disable/re-enable.

## Handoff G3 và phương án tích hợp

- **Đợt 1:** P12 và P13 có thể phát triển song song ở module riêng. Chốt một writer cho từng đợt tích hợp `app.rs`, `routes/mod.rs`, `storage/mod.rs`, `App.tsx`, `AdminShell.tsx` và API barrel. Hoàn thành integration của một feature trước khi feature kia sửa cùng file. Migration names/version cấp khi G3 được duyệt và cập nhật theo `main` trước merge. Mỗi feature chỉ đạt Primary Acceptance khi qua entry point bình thường cùng backend.
- **Đợt 2:** P14 sau khi P13 ổn định public context. P15 chạy song song ở feature/plugin API client. P10 có thể chạy sau P09 khi có lượt tích hợp Dashboard. P17 và P19 nghiệm thu cùng candidate SHA sau khi mọi feature merge. P18 nằm trong P19 trừ khi tái hiện lỗi cần gói sửa riêng.
- `STOP_AND_PROPOSE` nếu thay hành vi G0, có mất dữ liệu, API/ABI/security cần đổi ngoài contract, hoặc evidence bắt buộc không đạt. G3 cần source SHA đã merge, file ownership cụ thể, acceptance và trạng thái GitHub phù hợp. Bản ADR này không cấp Task ID hoặc trạng thái Project.
