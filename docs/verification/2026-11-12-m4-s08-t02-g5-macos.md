### Rollback sequence verified with actual binaries

1. **Old:** launch `062b493` on a new temporary site. Set up Admin, a published
   CPT with two records, two published Posts plus one draft Post, an actual
   uploaded image, an old-format Builder Heading and Text with an existing
   binding and responsive data. Save with old API; verify escaped homepage,
   published-only exact binding and no List Block. Shut down the old server.
2. **Snapshot:** back up the original SQLite database through the SQLite online
   backup API and hash the complete rows of eight relevant tables and all
   uploaded media bytes, including the migration table. Validate FK/integrity.
3. **New:** open the *same* site under the exact `09900e6` release. In real
   Chrome add and configure two `core/list` nodes in Inspector: published
   Projects ordered ascending (one/page), and published Posts ordered descending
   (one/page). Preview shows only their first pages and does not persist draft
   state. Save through Chrome UI; verify incremented document version/ETag,
   both typed List props, preserved static/binding/responsive data, and
   separate public page-two results with irrelevant query parameters discarded.
   Published results never include the draft Post.
4. **Changed rows:** SQLite snapshot after new Save differs only in
   `builder_homepage`. Content types, entries, taxonomy, media tables,
   migration records and actual uploaded-media SHA-256 values are identical.
5. **Old editor on new data:** create an independent copy of the new SQLite
   state and assets. Reopen it under the old release **and old embedded Chrome
   Admin**. Both new List nodes are unresolved and not rendered publicly,
   but remain anchored in the old document. Edit an unrelated Heading in the
   old UI and Save; assert both List nodes remain byte-for-value equal in
   saved JSON and preserve order/ID/typed props, binding and responsive data,
   with no draft leakage. Reopen that copy under the new release: both lists
   reappear with working independent pagination.
6. **Restore:** copy the *original pre-change* SQLite backup and media into a
   third disposable site; reopen with the matching old release. Confirm
   original document and homepage, matching SQLite row fingerprint, FK and
   integrity checks, migration 14 and exact uploaded-media hashes.
