A separate P2 found by independent review was the deletion of a post/term whose prior canonical path used a nonlegacy rewrite (`/blog/{slug}`, `/genres/{slug}`). `sync_claims_in_tx` moves the previous claim into dead history when the stable ID is deleted. The old code inferred orphan family only from the **same URL** when it used the protected legacy spelling, incorrectly returning 409 on rewritten canonical paths and rolling back an otherwise legitimate delete. The change to `src/storage/permalinks.rs` infers deleted owner family only from its exact `(target_kind, stable ID)` protected legacy history (`/content/{type}/{slug}` or `/taxonomy/{kind}/{slug}`), never from arbitrary rewrite/custom URLs. Conflicting or absent proofs fail closed. The tests now prove rewritten post and term deletes succeed, former URLs stay 404, and an orphan post alias cannot shadow a newly selected CPT rewrite family. No migration/schema change, ACL override, or public fallback.

Independent review also identified an N+1 sitemap performance regression: a part containing up to 5,000 indexable routes triggered up to ~5,000 individual canonical-claim queries after the indexable CTE query. `src/storage/sitemap.rs::list_indexable_routes_in_tx` now pages **first** over the unchanged ACL/noindex/publication-filtered CTE, then resolves the bounded page with a single `LEFT JOIN permalink_route_claims` keyed by `(target_kind, target_id)` (entry/term stable ID, archive CPT key); only home `/` remains a fixed path. No legacy URL reconstruction, extra schema, changed sort/pagination/limit or widened visibility. The targeted sitemap integration PASS and independent static SQL/security review found no actionable P1/P2.
