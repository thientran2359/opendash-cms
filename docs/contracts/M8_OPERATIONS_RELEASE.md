## 2. Instance leases and mutation barrier — D01

`operations::SiteCoordinator` owns resolved SitePaths, lifetime instance locks and shared admission. Before migration/startup cleanup, canonicalize root and DB parent, reject symlink/reparse roots/escape, resolve relative overrides once against startup cwd and create allowed parents. Acquire nonblocking exclusive File::try_lock on `<site_root>/runtime/site.lock` and `<canonical_db_parent>/<db_filename>.opendash.lock` in sorted canonical-path order, keep handles until graceful shutdown. Another server/CLI mutator using either root or DB fails with stable busy code; never unlink a lock file to acquire it. Server lock handles must not leak to child processes. Existing plugin workers are trusted same-executable processes under the same OS identity; Wasmi guests lack a filesystem ABI, but this is NOT OS-level filesystem sandboxing of the trusted worker. Local NTFS/ext4/APFS only; NFS/SMB/shared roots unsupported. A local privileged program editing DB/files outside CMS is outside this consistency guarantee.

All state-changing paths acquire a `MutationLease` before staging/network-side-effect admission and retain it through filesystem finalization, DB commit, post-commit hooks/logs and terminal SMTP attempt persistence. Coverage includes auth/session/bootstrap/users, content/schema/taxonomy/publication/SEO, all Builder variants, settings/menu/import, theme/plugin lifecycle/KV/host actions/logs, image/video upload, contact/notifications/secrets, startup recovery and maintenance. GET handlers with real DB writes also participate; do not rely on HTTP method middleware alone. External SQL tools are prohibited while CMS runs. Every top-level mutator is enumerated in a checked-in writer inventory and audited/tested at S01; recursive inner calls borrow the lease, never reacquire and deadlock. Plugin admission context cannot forge one.

Backup/reconcile obtains exclusive maintenance: reject NEW writers503 + Retry-After3, let existing leases drain <=30s, fail busy without changing files if drain fails; do not kill in-flight mail and assume rollback. Public read-only delivery remains available. Maintenance owns a distinct unforgeable context for job bookkeeping/storage calls; no ordinary bypass. Wait for expired admissions/worker cancellation to be acknowledged, not only future-drop. Frozen source has zero outstanding filesystem writes, secret rotation, plugin KV commits or notification terminal updates. Snapshot file copy/VACUUM/hashes occur before releasing the barrier; encryption of completed private snapshot occurs after release. Operations workers establish native memory limits BEFORE reading untrusted input: Windows Job Object process committed-memory cap512MiB/kill-on-close, Linux RLIMIT_AS512MiB, native macOS allocation-limit equivalent verified by stress fixture (unsupported enforcement blocks that platform). Lifeline and CPU/wall budget supervise each worker; no inherited backup passphrase in argv/env, no core dump secrets. Resource limits apply to trusted operation workers, not a claim of OS isolation for existing plugin workers. Max frozen interval120s, checks between bounded chunks; cancel/failure discards private snapshot and reopens admission only after all copy/SQL work is stopped/joined. Snapshot/VACUUM runs in a dedicated trusted same-executable --operations-worker (snapshot mode) process operating only on read-only source access and generated private staging. Parent passes a bounded validated request over anonymous pipes, never an HTTP path or shell command; no passphrase in argv/env. Parent alone may publish artifacts/job success. At120s cancel then kill/wait child and verify exit before reopening admission; if OS cannot confirm termination, remain maintenance-blocked and record failure rather than promise a hard real-time bound. A lifeline watcher exits child on parent pipe EOF; restart marks abandoned job interrupted and never publishes its output, and does not delete a possibly open private staging tree until worker exit is confirmed. Source data is never modified by snapshot worker. Dropping a SQLx future alone is not proof of cancellation.

Durable ledger `operation_jobs(id64hex PK,kind,state,actor_id,version,phase,created_at,updated_at,artifact_id NULL,diagnostic_code NULL)` plus singleton monotonic maintenance_generation. States queued/running/succeeded/failed/cancelled/interrupted; compare-and-set transitions, only manual job creation, max200 retained receipts, no unbounded queue. One heavy job per site (backup/restore/reconcile/purge); conflicting admission409. Job operation timeout15min total, public upload max5min; maintenance120s subbudget. Server restart marks running jobs interrupted and performs finite journal recovery, no automatic mail/backup retry. Job state contains no passphrase/absolute path/raw error. New operations endpoints need Admin+CSRF+Origin, JSON<=8KiB, If-Match on mutable job/delete actions; same 401/403/409/412/428 conventions as M7. Public routes never serve runtime/backups/secrets.

## 4. Canonical snapshot and manifest — D03 / P01

`backup::create_snapshot(paths,exclusive_context)->SnapshotReceipt` copies only declared managed data under freeze into private `backups/.staging/<job_id>/snapshot/`. DB source is actual SitePaths.db_path, even external; `storage::backup::vacuum_into_snapshot` executes VACUUM main INTO a bound, generated destination using a dedicated SQLx connection outside any open transaction. Require complete destination, integrity_check=ok, foreign_key_check empty and migration checksums/current version consistent. Do not copy live sqlite/WAL/SHM or serialize entire DB into memory. Sync snapshot file/parent; no source mutation/VACUUM on live DB.

Manifest v1 strict DTO: `{format_version:1,app_version,source_sha,schema_version,migration_checksums,created_at,files:[{entry_name,kind,logical_key,size,sha256}],restore_policy_version:1}`. Sorted stable logical keys, max20000 payloads and manifest<=8MiB, <=4GiB total decrypted ZIP, DB<=1GiB, other single file<=512MiB. Count/hash actual read bytes,64KiB buffers; do not trust archive size metadata. Whole backup over limit fails with explanation, never partial success. Source root/absolute DB path, credentials, machine SID, environment secrets, keys/passphrase excluded from manifest. File hashes are integrity within encrypted artifact, not publisher signatures.

Canonical inclusion: database as `db/main.sqlite`; all active/retained media metadata files and existing thumbnails; every DB-referenced immutable theme/plugin revision plus valid retained canonical revision/archive state; installed legacy package data still stored in DB; current and retained SMTP secret blobs required by settings/attempt snapshots; strict `config/site.json` effective portable runtime configuration: snapshot schema defaults when file absent, and capture only allowlisted effective portable settings (not absolute root/DB path, secrets or arbitrary environment). S06 may change runtime trust implementation but not the versioned portable format without a contract delta. Referenced missing file/hash mismatch blocks backup. Journal-owned quarantine objects and retained delete receipts are included under private logical quarantine keys with generated job IDs; restore rebases those paths/receipts and never publishes them. Pending moving/tombstoned jobs must first recover or snapshot fails; finalized/quarantined receipts with retained files remain backup-owned private state. Canonical unreferenced media files are included in a quarantine category when safe grammar validates them, restored privately rather than published; unknown/uninspectable objects fail backup and require reconcile. Never recursively copy repo/executable/node_modules, external runtime environment, WAL/SHM, logs, sockets, instance locks, temp files, other backup artifacts or restored-site copies. Pending import/delete state must recover or abort snapshot, not be omitted while it owns files.

Archive payload entries are FLAT generated names `00000001.bin` etc plus manifest.json; original physical paths are not ZIP entry names. Before ZipArchive::new, preflight ZIP32 EOCD bounds/count/offsets/central directory<=16MiB/entries<=20001, fixed generated ASCII name<=13 bytes, zero archive/entry comments and zero extra-field bytes; reject ZIP64, overlapping/out-of-file offsets, excessive declared counts and any compressed method other than Store. Writer format1 must satisfy same policy; total4GiB includes ZIP metadata, not only payload. File backing alone does not bound archive-parser allocations. Restore maps validated logical keys through domain constructors, never joins an arbitrary manifest path. File kind grammar: DB one fixed path; private quarantine generated job/object keys; media canonical SHA/shard/ext/thumbnail; package validated packageID/revision digest and original allowlisted filename plus .complete; secret64hex refs only; fixed config object. Casefold/Unicode/Windows reserved-name/ADS/path collisions forbidden even on Linux. Reuse package::ensure_safe_flat_entry and common size/checksum logic; add file-backed bounded ZIP profile without weakening existing Theme/Plugin caps or allowing directories/links/encrypted ZIP entries. Store ZIP payloads uncompressed to avoid expansion ambiguity; future deflate restore is rejected by format1 profile. Snapshot bytes are immutable after receipt; exclusive barrier released only after DB/files/manifest verify as one cut.

## 6. Restore-to-new-site, recovery and activation — D05/D06 / P03

Admin streams encrypted artifact POST `/api/admin/operations/restore-uploads` (raw application/octet-stream<=4GiB+2MiB (4297064448 bytes) including age envelope/authentication overhead,5min) to private generated incoming ID, bounded64KiB, no caller path. POST `/api/admin/operations/restores` `{upload_id,passphrase,request_id}`=>202. Service validates full AEAD stream before trusting ZIP, preserves plaintext only in private staging; bad password/tamper/trailing unexpected data/ZIP policy/manifests/checksums/foreign DB/unknown newer format/schema/forged-ledger malicious schema objects fail before publication. Decrypt header/KDF and body caps checked incrementally. No executable is restored/run from archive. Existing package validation is reapplied; malformed immutable revision/.complete/digest, cross-owner declarations or referenced secret/media missing rejects restore. Foreign snapshot must contain a viable Admin account; password hashes preserved, not bypassed by bootstrap.

Server chooses new root `<site_root>/backups/restored/<job_id>/`; stage is sibling `.restore-<job_id>` on same filesystem, final path must not exist and cannot equal/contain source canonical DB or managed paths. No arbitrary target/overwrite current root or external DB. Restore unpacks through logical-key constructors, creates private ACLs locally (never copies source OS SID/mode blindly), rebases database to target `database/opendash.sqlite` regardless source external path, validates declared config with safe loopback listener defaults and unknown env overrides rejected. Missing passphrase has no recovery backdoor. Source data/site/network configuration unchanged.

Open restored DB in the isolated operations worker, first read-only/defensive mode with trusted_schema=OFF and extension loading disabled. Bound schema metadata before materializing it: <=256 objects, <=256KiB SQL/object and <=2MiB total SQL, checked via length/count queries under worker cap; malformed/overbudget rejects. Before ANY sanitize/migrate/write, validate sqlite_schema type/name/table/DDL fingerprints against compiled known schema at the declared version, including exact legitimate migration0008/0012 triggers and SQLite internal objects. Migration-ledger hashes alone are not schema authenticity: reject extra/modified trigger/view/virtual-table/index/table objects or divergent definitions even if ledger/file hashes were forged. Build fingerprints deterministically from compiled migrations on supported bundled SQLite; reject unknown schema variants, do not execute arbitrary schema to discover them. Once validated, reopen COPY for permitted writes/migrations only, extension loading still disabled; support first format1 archives from M8, same/older app schema supported by compiled migrations, reject newer schema or divergent history. Clear sessions and stale auth/CSRF tokens, clear active operation leases/queues; pending/sending SMTP attempts become unknown/disabled as appropriate with no sends, settings SMTP enabled=false. Preserve users/content/layout/menu/schema/options/plugin revisions/KV/submissions/metadata and IDs. Retain a generated recovery_safe_mode=true config: noindex public pages, anonymous contact writes denied503, plugin execution/external calls denied, operations/Admin recoverability available. Do not erase stored plugin enabled flags to simulate data preservation. Restore validation never spawns guest or mail/network side effects.

After integrity/media/package/secrets checks, fsync files and directories, close DB pools/handles/WAL, write READY manifest with target hash/schema, atomic same-volume no-replace rename to final generated root. Only then succeed; API returns restore_id/sanitized status/relative location, never source paths/secrets. Interrupted pre-READY job remains private staging and can be explicitly discarded/restarted; unexpected final target or ambiguous rename is inspected, never blind retry/overwrite. Completed restored root is never cleaned as temp. No automatic archive-driven startup/activation.

Admin UI explicitly says restore creates a separate recovered site. Operator uses documented single executable with OPENDASH_SITE_ROOT pointing to that root and OPENDASH_DB_PATH unset, checks loopback health/Admin/re-edit, then changes service/proxy mapping during a maintenance window. Previous site root/binary retained for rollback; do not edit a running DB file. This is operator activation, not a claim of atomic multi-volume hot swap. In restored target, POST `/api/admin/operations/recovery/activate` requires Admin session+CSRF+Origin plus current password confirmation and matching READY generation; clears only runtime safe mode with durable config update. SMTP remains disabled until explicit settings enable; no pending actions replay. User-facing workflow exposes restored-copy status and activation requirement without server secrets. S05 acceptance must demonstrate full Admin restore then operator start/login/edit/Save/public and rollback; creating an archive alone is insufficient.
