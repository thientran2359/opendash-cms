## Overview

OpenDash will give content editors a recoverable deletion workflow and let them perform small, common edits without opening the full entry editor. The existing content table remains the main workspace. Trash is independent of publication state: an entry may retain its previous publication information for recovery, but it must not be publicly accessible while trashed.

The feature covers built-in Post and Page and ordinary custom post types (CPTs) owned by the site or active providers. It extends the current table selection workflow rather than introducing a separate task engine. The design must preserve entry identity, locale, translation group, content, and references while respecting the existing Admin/Editor roles, publication policies, and provider ownership. The separate retained-Trash maintenance view is limited to Admin for inactive/withdrawn ordinary CPTs; it is not ordinary editing or a plugin capability.

The product context is [V1 requirements](../product/PRODUCT_REQUIREMENTS.md), [Core Foundation](../contracts/CORE_FOUNDATION.md), [Plugin ABI](../contracts/PLUGIN_ABI.md), [Writer Inventory](../contracts/M8_WRITER_INVENTORY.md), and the [design catalog](../designs/SITEMAP.md).

## The Problem

Today the generic Admin delete operation physically removes the entry. A mistaken click can require recovery from a backup; there is no entry-level restore. Deletion can also affect URLs, SEO, media references, Builder documents and translations. A content table filter alone cannot make deletion recoverable: multiple public readers and ordinary mutation paths currently use the draft/published flag or entry version without any lifecycle state.

The current table already has selected-page Publish, Move to Draft and Delete operations with per-entry compare-and-swap (CAS, rejecting a write if its expected version has changed) and partial results. Publication actions in the UI are restricted to Post/Page even though the bound publication endpoint already handles eligible CPTs. Taxonomy changes still require individual edits. There is no inline Quick Edit for title, slug, publication date and taxonomy; using the existing full editor payload from a table would risk overwriting unrelated or inaccessible fields.

Two release-blocking invariants are required before activation: no fresh public read of a trashed entry (or its exclusive media grants), and no ordinary write to a trashed entry. Retention is not public access; durable commit is not secondary hook delivery.

## Goals

* **G1 — Recover accidental deletion.** For ordinary entries, replace the human-facing destructive delete workflow with Move to Trash. Trash retains entry ID, body and private fields, Builder data, SEO, media/pattern references, locale, translation group, slug and eligible route reservations. An Editor or Admin may recover an entry subject to existing content permissions and current schema/provider/locale eligibility. Draft/publish entries restore as draft; immediate-mode entries restore to their existing immediate publication policy, with explicit warning if publicly visible. Restore conflicts leave the entry in Trash without partial changes. Translation siblings are not changed automatically.
* **G2 — Prevent disclosure and unintended writes.** Once the trash transaction commits, no fresh public read may expose content or media access attributable solely to the trashed entry. Ordinary editor, Builder, SEO/route, translation, publication and plugin mutation paths must reject a trashed target, even with a current version. Previously authorized independent media sources remain valid. Every lifecycle transition advances the entry version; stale concurrent edits fail without overwriting data.
* **G3 — Deliberate permanent deletion.** Manual retention with no automatic expiry. Only Admin or an explicitly granted plugin action operating under a currently authorized Admin principal may purge a trashed entry, after explicit irreversible confirmation. Purge removes retained entry-dependent data using the existing cleanup invariants. It must not make an unrelated entry or shared asset inaccessible. Assigned homepage/posts pages cannot be trashed until reassigned; Private Pattern remains separately managed in Studio Mode 2; retired Section/legacy Builder workflows are not revived. No promise of URL reuse after purge where existing historical redirect rules reserve a route. Ordinary plugin content_delete moves the entry to Trash; plugins also have explicit scoped Trash discovery, restore and purge operations. Plugins cannot bypass Trash, exceed the current actor role or acquire additional permissions implicitly. Admin-only retained-Trash maintenance is specified separately below.
* **G4 — Consistent management UI.** Provide All (active only), Published, Draft and Trash views with authoritative counts under the same type, locale, search and taxonomy filter scope. Immediate-mode types omit unsupported publication controls. Trash shows the previous publication status and deletion date; row and multi-row actions offer only valid operations, with clear blocked reasons. Normal list, Single Edit and Studio must agree on lifecycle restrictions. English and Vietnamese Admin labels are complete; content locale is independent of Admin language.
* **G5 — Quick Edit.** Edit title, slug, eligible taxonomy, explicit publication status where supported, and actual publication date in a single small inline form. Never change created_at as a substitute for publication date. Keep unrelated terms, primary category unless explicitly affected, body, hidden fields, Builder and SEO data unchanged. A never-published draft does not set a future publication schedule. Publication-date edit eligibility and time conversion are specified in the Technical Plan. Preserve authorized dirty input after 401 authentication expiry or 412 stale-version conflict and offer an explicit refresh/rebase path.
* **G6 — Bulk Actions.** Expand the existing current-page selection to at most 100 entries per operation. Support Publish/Move to Draft for eligible draft_publish types, add/remove/replace in one explicitly selected eligible taxonomy (preserving other memberships), Trash, Restore and Admin-only permanent deletion. Each item has its own version-checked transaction. Show succeeded, stale/conflict, confirmed failed, uncertain (commit unknown), and unattempted outcomes; stop on authentication loss or scope change, reconcile results, and never replay committed successes automatically.
* **G7 — Safe upgrade and maintainable operation.** Preserve populated database IDs, foreign keys and all pre-existing entries through migration; no existing entry becomes trashed during upgrade. Guard old binaries and legacy Admin clients from unsafe behavior. Keep the Rust/SQLite single-executable deployment and existing service boundaries. Measure list/count latency, batch duration, writer lock time, memory/WAL and hook pressure using baseline and representative datasets (1k, 10k, 50k entries, selections of 20 and 100). Use the quantitative acceptance budgets in Performance, bounded resources and diagnostics; results require future measurement. Provide privacy-safe operation diagnostics without logging content or secrets; do not claim exactly-once hooks.

## Non-Goals

* Trash for media files, taxonomy terms, menus, private Pattern; reviving retired Section/legacy Builder endpoints or changing their existing separate contracts.
* Automatic retention expiry, scheduled publication, a background scheduler, revision history, or undo history beyond restoring an entry.
* Whole-site/all-pages bulk selection, multi-type or cross-locale batch operations, a new durable job engine, or global all-or-nothing batch transactions.
* Cascading trash or restore across translations, changing provider ownership, unconditional Admin authority for plugins, or expanding plugin capabilities outside the owner-requested entry lifecycle operations. The existing SDK/ABI is extended only as needed for scoped Trash discovery, restore and purge.
* New third-party runtime services, remote telemetry, new Admin roles, or changing the existing backup/restore and locale-orphan-purge workflows. The latter remains an explicitly confirmed destructive maintenance action.
* Redesigning the full Entry Editor, Studio, or content table; changing theme trust/security policy or live site data.

## Critical User Journeys (CUJs)

### CUJ 1: Recover a mistakenly trashed article
* **Given:** An authorized Editor has a published Post with a canonical URL, translations, media and Builder content.
* **When:** The Editor moves it to Trash, then restores it from the Trash view.
* **Then:** The active table and public reads exclude the trashed entry; all recovery data remains. Its sibling translations and independently referenced media remain unchanged. Restore returns the same ID to draft, preserves the publication date, and does not publish until explicitly requested.

### CUJ 2: Immediate content and protected pages
* **Given:** An immediate-mode ordinary CPT entry and a Page assigned as the site's homepage or posts page.
* **When:** An authorized user trashes the immediate entry, restores it after a warning, and attempts to trash the assigned Page.
* **Then:** The immediate entry is hidden during Trash and restored under current immediate policy; the assigned Page action is blocked until reassignment. No silent settings change occurs. An attempt to assign an already trashed Page is rejected.

### CUJ 3: Prevent stale or unauthorized changes
* **Given:** An Editor has an old open form or Builder session; an Admin has moved that entry to Trash.
* **When:** The Editor or plugin attempts to save, publish, edit SEO or write using either a stale or newly retrieved version.
* **Then:** The mutation does not change canonical data, visibility or lifecycle; the client receives actionable feedback. Restore or authorized purge remains explicit. A pre-trash projection calculation cannot restore a public projection after the trash commit or overwrite the restored version.

### CUJ 4: Quick Edit without losing content
* **Given:** An ordinary active entry with multiple taxonomies, private fields, body and SEO metadata.
* **When:** The Editor changes its title, slug, eligible category or publication date inline, encounters a stale version, and refreshes/rebases the authorized draft.
* **Then:** The final save changes only intended fields through existing permission/schema/route invariants, preserves unrelated values, and does not silently publish a draft. The site timezone is displayed and stored date is canonical UTC. No unapproved overwrite happens.

### CUJ 5: Mixed-result bulk operation
* **Given:** A selected current page of entries containing valid rows and stale/conflicting rows.
* **When:** The user changes publication status or adds/replaces/removes terms for one taxonomy; authentication expires partway through a second batch.
* **Then:** Each committed row remains committed, stale/conflicting rows are untouched, unrelated taxonomies survive, and remaining rows are reported unattempted. A fresh authorized session reconciles current versions and may retry only appropriate rows. Counts and page selection reload from server state.

### CUJ 6: Permanent deletion and upgrade safety
* **Given:** A populated pre-feature database with existing entries, and later an Admin and Editor viewing Trash.
* **When:** The database upgrades, the Editor attempts purge, and the Admin explicitly confirms purge of a trashed entry.
* **Then:** Upgrade preserves existing records and relationships; Editor purge is denied; Admin purge removes only the specified entry and its dependent data per the existing cleanup contract. Shared references remain intact. Unsupported old binaries cannot expose the newer database's trashed content. A supported pre-upgrade backup remains recoverable.

### CUJ 7: Authorized plugin lifecycle parity
* **Given:** A plugin has explicit CPT-scoped lifecycle permissions and an authenticated Admin invokes its action.
* **When:** The action moves an entry to Trash, discovers the retained entry, restores it, or requests a separately confirmed purge after it is trashed again.
* **Then:** Each transition follows the same shared storage rules as the equivalent Admin action. An Editor invoking the same purge action, a plugin without the grant, a stale actor/generation/version, or an unconfirmed or active target cannot purge. Ordinary public and private plugin content reads still exclude Trash. No additional authority follows merely from installing a plugin.

## Technical Plan (Architecture)

This plan translates the owner-aligned product direction into explicit contracts. The implementation plan below fixes the interfaces and ownership; this revised specification has Owner approval; implementation may start only after merge and Issue readiness.

### 1. Lifecycle model and transitions

Add a nullable UTC `trashed_at` column to `content_entries` in the next available additive migration (0053 at this baseline; allocate the number against main before implementation). NULL means active; non-NULL means trash. The original draft/published value is retained while trashed; it is not a visibility flag on its own. Preserve the existing primary key, foreign keys, unique (type, locale, slug), unique (type, translation group, locale), `has_been_published`, and publication date. Do not copy rows to another table, change the publication enum, or add a scheduler. Do not attach an actor FK that makes restoring a row depend on a user's continued existence.

| Current state | Operation | New state | Allowed actor and preconditions |
| --- | --- | --- | --- |
| Active draft or published | Trash | Trashed, original publication state retained | Admin/Editor with existing content permissions; ordinary active CPT, manageable locale, matching version, not an assigned Reading Page |
| Trashed, draft_publish CPT | Restore | Active draft | Same content permission; current schema/provider/locale and route checks pass |
| Trashed, immediate CPT | Restore | Active published | Same checks, current immediate policy; explicit warning/confirmation before public exposure |
| Trashed | Purge | Physically absent | Admin or explicitly granted plugin acting under an Admin principal, matching version, explicit host-controlled irreversible confirmation |
| Active | Purge | No change | Reject; must first move to Trash |
| Trashed | Normal save, publish, Builder, SEO, route, translation creation, provider write | No change | Reject, even with correct current version |
| Active | Normal save or publication change | Existing rules | Existing CAS, role, schema, locale and admission checks |

Repeated invalid transitions return a conflict rather than creating extra versions. Every successful trash/restore increments version exactly once, updates updated_at and preserves created_at/published_at. A draft-capable restore must not emit a publish event; a subsequent explicit Publish is a separate action. Immediate content is restored according to current publication policy, not an invented draft state. No cascades across translation groups.

Keep the existing guard against converting a draft-capable CPT to immediate when retained draft rows exist, including Trash; do not discard or rewrite the retained status to evade the guard. A trashed entry whose provider is inactive/withdrawn or whose locale has been deleted or parked remains stored; ordinary restore requires reactivation or recovery under existing settings. For a disabled secondary locale, use the existing Admin management rules for visibility in tables, but prohibit restore until locale is enabled and multilingual mode is active. For an inactive/withdrawn ordinary CPT, Admin may explicitly discover retained Trash metadata and purge a selected trashed row via the retained-Trash maintenance scope defined in §7; no normal edit, provider execution, restore or additional Editor/plugin authority. For a disabled/parked locale not currently manageable, re-enable it before per-row operations. Deleted locales remain accessible only through the existing orphan recovery/purge workflow, including trashed rows. No new broad access to dormant data. Existing explicitly confirmed locale-orphan purge is a distinct maintenance operation; it continues to remove its scoped data and must count trashed rows. Ordinary Trash APIs do not provide a bypass. Restore examples: an inactive provider or disabled locale requires reactivation; an invalid required field, incompatible term or route collision blocks restore atomically until repaired; compatible withdrawn values/terms remain intact. Never silently discard data.

### 3. Writer and side-effect boundary

Use the existing AdmittedMutation lease, role/CSRF guards, SQLite writer reservation and CAS. Validate type and actor before disclosing whether a target exists. Under the reserved writer, reload current entry version, lifecycle, type settings, locale and relevant schema, reference and authorization fences. Ordinary writers require active lifecycle; restore and purge require Trash. Apply all dependent writes, projection invalidation, public SEO reference synchronization and required route-claim consistency in one transaction. Extract one storage-internal physical_delete_cleanup_in_tx helper accepting the already reserved transaction; both legacy deletion paths reuse it before activation and only explicit authorized Purge calls it after activation. It never starts or commits a transaction; authorization and CAS remain outside cleanup in the same writer. Return the committed version/state from the transaction rather than a second read that might observe another writer's result.

The closure inventory includes direct entry saves and composite saves, publication, translation creation, Builder save/reset, SEO and route edits, provider actions, plugin staged commits, Reading settings, import and provider/schema maintenance. Source anchors: `storage/entries.rs:687-706,2607-2650,3241-3335`, `storage/builder.rs::save_entry_builder/reset_entry_builder/read_entry_builder`, `storage/seo.rs:826+`, `storage/plugin.rs::delete_entry_with_plugin_fence`, and `docs/contracts/M8_WRITER_INVENTORY.md`. Explicit maintenance paths that need access to retained data keep their own guards and cannot be mistaken for ordinary editing. No SQL in routes and no database or HTTP work in opendash-core. Audit main.rs startup normalization (storage::builder::migrate_demo_entry_builder_docs_on_startup) and typed override selectors; existing maintenance may transform retained data under its own guards but cannot resurrect a row or reintroduce retired grants.

For projections, invalidate stale public rows inside lifecycle or relevant metadata mutation. Calculate the new projection only outside the writer lock, then verify the source entry version, lifecycle, provider generation/eligibility and locale under the writer before persisting. A computation for an old version must not overwrite or delete a newer version's projections, including after trash and restore. A projection failure after commit cannot turn a committed write into a reported database failure; return committed status and secondary work outcome, log an actionable reason and reconcile using the existing recompute path. Define the same semantics for the existing publication endpoint used in bulk. Public reads never invoke plugin Wasm to fill the gap.

Preserve existing best-effort asynchronous hooks and their bounded queue (2 workers, 64 pending jobs; ABI contract section 5). Trash of a published entry emits ContentAfterUnpublish after commit with explicit lifecycle context; trash of a draft emits no publication event. Restore of an immediate-mode published entry emits ContentAfterPublish after commit; draft restore emits no publication event. Purge alone emits ContentAfterDelete. Lifecycle transitions are not ordinary content edits and do not call prepare_save/before_save. Do not invent a new hook enum or claim guaranteed delivery. Existing publication-status semantics also apply to private immediate types; visibility still depends on CPT policy. Add optional lifecycle context to relevant payloads only after checking schema 1–3 compatibility. No false Delete hook for Trash. Enqueue only for committed transitions; queue drops, maintenance cancellations and plugin execution failure are observable, not grounds to repeat a mutation.

### 4. API and authorization contracts

All paths are relative to `/api/admin/content-types/{type_key}/entries/{id}`. New handlers reuse requestJson/requestText, no direct fetch, existing CSRF and admission controls. JSON input rejects unknown fields and uses an explicit body limit; every mutation uses the existing If-Match entry-version header. Explicit permission checks precede entry lookup. Type/ID/locale are server-resolved; no cross-locale or cross-type mutation through payloads.

| Method / suffix | Purpose | Request | Response on success |
| --- | --- | --- | --- |
| POST /trash | Move to Trash | Empty JSON object | 200, lifecycle summary and new ETag |
| POST /restore | Restore | Confirmation flag only for immediate public restore | 200, lifecycle summary and new ETag |
| DELETE /purge | Physical delete of trashed entry | Existing If-Match; Admin; explicit `X-Confirm-Purge: true` header; optional `retained_trash=true` query only for Admin dormant maintenance | 204, no-store |
| PATCH /metadata | Quick Edit and single-taxonomy bulk delta | Narrow patch described below, schema token and entry If-Match | 200, updated authorized summary, ETag, committed secondary work outcome |
| POST /publication | Existing publication transition | Existing status input + If-Match | Preserve existing compatible entry response, guard lifecycle and expose secondary failure without misreporting commit |
| DELETE (legacy) | Compatibility endpoint | Existing If-Match | At S02 activation: move to Trash with existing 204 response for authorized active ordinary entries, reject trashed targets; document semantic change |

The lifecycle summary contains id, type_key, locale, version, publication_status, trashed_at and published_at; it never returns private values or a public URL for Trash. Use no-store headers. The UI's irreversible confirmation explains exact selected entry identities/count; the server independently enforces role, state, version and explicit operation intent. Confirmation is not authentication.

At activation, legacy DELETE is a recoverable alias with unchanged 204 success. No ordinary hard-delete bypass.

Typed failure reasons, reusing existing error transport where possible (stable reason prefix in text/plain for existing callers, structured code for new operation response if needed): 401 unauthenticated, 403 permission/CSRF, 404 unknown or wrong scoped resource, 428 missing CAS or required schema token, 412 stale entry version or required schema token, 409 incompatible state/schema policy/route/provider/Reading assignment/timezone change, 422 invalid patch, taxonomy, date or hook veto; use existing maintenance admission status. For an authorized existing row, compare version under the writer before checking transition eligibility so stale clients get 412; no leaked conflict details to unauthorized users. Return bounded reason codes and localizable messages; no raw SQL, field values or secrets.

### 5. Plugin lifecycle parity

An authorized plugin acting for an Admin has the same ordinary eligible entry lifecycle operations as Admin; it is not a new global Admin principal. An Editor-context action cannot exceed Editor rights. Retained dormant-provider maintenance is an explicit Admin-only core exception, not a guest operation.

The existing ABI content_delete stages one physical delete for an allowed CPT with a manifest grant, declared action capability/role, generation fence and CAS (PLUGIN_ABI.md:140-143, plugin/manager.rs:711-734, storage/plugin.rs::delete_entry_with_plugin_fence). At S02 activation, route it to the shared Trash transaction. Add the following opt-in operations; preserve the existing envelope and type-scoped permission conventions:

| Host operation | Manifest/action grant | Effective actor | Contract |
| --- | --- | --- | --- |
| content_delete | Existing content_delete | Admin or Editor, within current permission | Active entry to Trash; existing request/result shape |
| content_trash_list / content_trash_get | New content_trash_read | Authorized Admin or Editor | Bounded metadata-only Trash discovery, active CPT and manageable locale scope, deterministic trashed_at DESC/id DESC order; version included for CAS; no private body or public URL |
| content_restore | New content_restore | Authorized Admin or Editor | Trashed entry to current permitted restore state; expected_version required |
| content_purge | New content_purge | Admin only | Trashed entry to physical removal; expected_version and host-authorized irreversible intent required |

All lifecycle writes are Standard authenticated Action mode only. No writes from public/filter/hook/background principals. Scope each grant to explicitly authorized content types, require the corresponding action capability, and validate role and permission at both admission and commit. New grants default absent and never derive from existing content_delete/content_write or plugin installation; require manifest_schema=3 and valid min_host_version >=0.1.1 for new grants, with host compatibility comparison. Use the existing staging protocol: one content mutation per invocation, no mixing with KV writes or another content command. Recheck plugin enabled state, revision generation, actor role/session, locale/type, entry version and lifecycle under the same reserved writer as the shared Admin transition. Protect assigned Reading Pages and keep private Pattern and retired Section restrictions. No direct active-entry purge and no separate plugin deletion algorithm. Trash discovery uses the same explicitly granted authenticated Action context; no dormant-maintenance bypass.

The host must obtain explicit Admin confirmation for purge and equivalent human consent for immediate public restore, binding the exact site, session/actor, plugin/action/generation, CPT/entry/version, locale, operation and origin. A guest-supplied confirm=true is never consent. Use the bounded single-use confirmation store and exact 409/confirm/cancel wire contract in S02. Do not hold a writer, admission lease or Wasm process across user input; reauthorize under fresh admission and reserved writer before commit. Ordinary content_get/list exclude Trash even with private grants. For actions declaring content_restore or content_purge, reject the http action capability at manifest validation and independently deny every HTTP host call before network I/O, regardless of operation order or whether confirmation is ultimately needed. This new-capability restriction leaves existing actions that declare neither grant unchanged. No KV or other content writes may be mixed with a staged lifecycle mutation. Pending/cancel has no canonical CMS mutation, lifecycle hook or guest external HTTP effect; bounded diagnostic logging remains allowed.

Return the actual committed lifecycle outcome through the plugin dispatcher. Apply the same projection invalidation and lifecycle hooks as Admin; no ContentAfterDelete for Trash, one post-commit delete enqueue attempt for actual purge, and no duplicate publication hook. Restore does not silently publish a draft-capable entry. Preserve existing best-effort hook delivery semantics.

The content_delete wire contract remains compatible but the physical-deletion behavior changes intentionally. Plugins relying on immediate row removal, slug release, cascade cleanup or hard-delete hooks must migrate to explicit content_purge after Trash and Admin confirmation. Document new opt-in grants, host operations, action capability allowlist, minimum host version, staged write rules and SDK wrappers/examples in PLUGIN_ABI.md, SDK and tests. Older plugin manifests retain their prior grants without implicit restore/purge. Use schema 3 and the exact 0.1.1 host minimum fence in S02; old hosts must reject new grants with that minimum. Verify schema 1–3 compatibility, denied grants/modes, actor role/session and revision changes, CAS, wrong type/locale, confirmation replay/substitution, active-target purge rejection, retained media and actual purge cleanup. The ABI change is specified here, not implemented.

### 6. Narrow metadata mutation for Quick Edit and taxonomy bulk

```text
MetadataPatch
  expected_schema_token: required
```

Omission means retain, not clear. Reject null where a nullable clear is not explicitly supported, empty/no-op patch, unknown fields, full values/body, custom path, content mode, SEO, locale, translation group, created_at and updated_at. Use existing title/slug validators and bounds; conflicts return actionable 409, not silent auto-renaming. Status is explicit and allowed only under draft_publish; never infer publish from date input. A date may be edited if the resulting state is published or a historic published_at exists. Never-published draft with no explicit Publish cannot set a date. If published_at is missing on a historic immediate entry, follow the existing date initialization invariant; the detailed plan must verify immediate create and restore behavior. Accept exactly ASCII YYYY-MM-DDTHH:mm:ss (seconds mandatory, no suffix or fraction; e.g. 2026-11-26T09:30:00), with the current IANA site timezone echoed; reject changed timezone, invalid or DST-ambiguous/nonexistent local time (ask for a valid unambiguous time), and times after server now. Use existing jiff dependency and current settings; store canonical UTC in the existing SQLite timestamp format. Preserve migrated historical dates (0049 backfilled from updated_at) until explicitly edited; do not describe those estimates as known first publication instants. Do not introduce scheduling.

Taxonomy operation refers to one currently eligible taxonomy, never all term IDs. Add means union; remove means subtract; replace means replace membership of that taxonomy only. ## Alternatives Considered

The alternatives below document architectural trade-offs.

### A. Add trash to the publication status enum

* Pros: existing published-only queries would exclude the new status in many cases; fewer new predicates in those readers.
* Cons: conflates publication and retention, requires remembering the old publication status, changes existing CHECK constraints and assumptions in immediate CPTs, Pattern, plugin responses and publication hooks. Other public and ordinary write paths still require an audit.
* Rejected by author: keep lifecycle independent with nullable trashed_at, retain publication metadata, and close every relevant public and writer path. A schema state that happens to hide some readers does not prove full isolation.

### B. Move entries into a separate Trash table or serialized archive

* Pros: separates live and deleted rows, simplifies some normal queries.
* Cons: moving canonical rows requires copying or remapping foreign keys, Builder data, terms, SEO, translations and media references. Restoration and uniqueness become harder; deletion cascades could destroy recoverable data.
* Rejected by author: preserve the canonical row and its relations. Separate visibility from retention, not identity from its dependencies.

### C. Use full editor PUT/composite requests from the list for Quick Edit

* Pros: existing save APIs and validation already exist; fewer endpoints.
* Cons: requires obtaining and returning fields the user did not intend to edit, creates stale data and ACL risks, couples table controls to editor body/schema details. Full term replacement can erase unrelated taxonomy membership.
* Rejected by author: use a narrow server-side metadata patch with the existing shared validation, storage commit and hook pipeline. Preserve full-editor behavior; verify plugin prepare-save interactions rather than bypassing them.

### D. One global batch transaction or a new asynchronous bulk-job engine

* Pros: all-or-nothing atomicity, centralized batch accounting, or durable continuation for large selections.
* Cons: longer SQLite writer occupancy, one conflict can fail every row, new persistence and authorization lifecycle, unnecessary scope for the existing bounded page selection.
* Rejected by author: reuse sequential per-entry CAS, at most 100 selected rows, with independent committed outcomes and reconciliation. Revisit only if measured lock or latency limits require a different strategy; do not introduce a scheduler or global transaction to mask performance problems.

### E. Automatic Trash expiry and purge

* Pros: limits retained storage and stale slug reservations.
* Cons: introduces unattended destructive writes, scheduling, retention settings, expiry races and backup considerations. Accidental permanent deletion is harder to recover.
* Rejected by author: manual retention and explicit Admin-authorized purge. Surface retained entries and measure storage/backup cost; do not silently expire them.

### F. Restore previous published state automatically

* Pros: restores the original public URL and publication status without an additional action.
* Cons: may unexpectedly republish old content; current schema, provider and locale can differ from the pre-trash state.
* Rejected by author: restore draft-capable entries as drafts and preserve their historical date. Immediate-mode content follows its current policy with explicit public-restore consent. Restore conflicts must retain Trash without partial mutation.

### G. Release slug, translation slot and route claims at Trash time

* Pros: users can immediately create replacements with the same identifiers or URLs.
* Cons: weakens recoverability and introduces competing claims, translation uniqueness conflicts, SQLite constraint changes and redirect ambiguity.
* Rejected by author: reserve identity and eligible route claims until purge, subject to existing routing rules. Explain reservations and conflicts in Admin; retention is not a public visibility grant.

### H. Ship Quick Edit and Bulk before complete Trash

* Pros: earlier delivery of lower-risk list improvements; metadata work can be independent of deletion lifecycle.
* Cons: invites parallel edits to shared routes, storage and table files; bulk Delete may retain destructive behavior while recovery is unavailable.
* Rejected by author for the release sequence: deliver S01 lifecycle closure and S02 recoverable workflow as one activation boundary, then S03 Quick Edit, then S04 Bulk. Independent preparation is possible only within non-overlapping ownership and approved contracts. Never expose a partial Trash feature.

### I. Retain direct physical plugin deletion of active entries

* Pros: preserves existing behavioral semantics, including old plugins relying on row removal or cascade cleanup.
* Cons: bypasses the recovery workflow. Restricting direct hard-delete to Admin-context plugins alone still leaves an exceptional active-entry deletion path.
* Rejected by author: the explicit choice of recoverable content_delete applies to ordinary entries regardless of actor. The later request for Admin parity adds explicit plugin restore/purge, not direct hard-delete of active entries. Existing request/response shapes remain; behavioral migration must be documented.

### J. Give every installed plugin all lifecycle rights or infer purge from content_delete

* Pros: fewer capability declarations; simple migration for plugins that used physical deletion.
* Cons: installation, an existing deletion grant or a guest-controlled flag would become an unintended authority escalation. Editor-context or compromised plugin actions could permanently destroy retained data.
* Rejected by author: authorized plugins have the same operations as Admin within the actor role and explicit CPT grants. Add opt-in discovery, restore and purge permissions; require host-controlled confirmation for irreversible purge. Do not allow a direct active-entry purge or a plugin-controlled confirmation bypass.

### K. Keep plugins limited to Trash with no restoration or purge API

* Pros: smaller ABI and fewer destructive capabilities to review.
* Cons: forces authorized Admin plugins to rely on manual UI operations and does not meet the owner's explicit requirement for lifecycle parity.
* Rejected by author: scoped plugin Restore and Purge are in S02, with the same state transitions and data-safety checks as Admin. The cost is an ABI/SDK extension, permission review, confirmation protocol and additional compatibility tests. This supersedes the earlier narrower brainstorm scope.

### L. Reject the legacy Admin DELETE endpoint at activation

* Pros: forces clients to explicitly choose the new Trash API; no change of meaning for a successful legacy request.
* Cons: interrupts existing Admin client deletion workflows even though a recoverable replacement with the same success response is available.
* Rejected by author: map legacy DELETE to Trash at S02 activation and keep its 204 response. Document the semantic change, reject invalid lifecycle transitions and reserve physical deletion for explicit purge.

### M. Add a durable hook outbox or an external observability service

* Pros: a durable queue could support eventual delivery and external services could simplify centralized diagnosis.
* Cons: adds a persistence/dispatch subsystem, reliability contracts, new failure modes and deployment complexity beyond the current best-effort plugin hooks.
* Rejected by author for V1: preserve the existing bounded hook queue, distinguish database success from hook/projection outcomes, and add privacy-safe local diagnostics and a repair procedure. Revisit durable delivery only with a separate demonstrated requirement.

## Non-Functional Requirements

### Security and data integrity

All ordinary entries must have a single retained identity; public eligibility, management access and conservative retention are separate predicates. No public read started after Trash commits may expose the trashed entry or a media grant derived solely from it. Existing authorized independent media references remain valid. No ordinary writer, plugin action or stale editor may change a trashed entry outside explicit lifecycle transitions. Enforce CSRF, type/locale/actor scope, schema and entry version, maintenance admission and plugin revision generation at the correct transaction boundary. Never trust guest output as evidence that a mutation committed or that a human confirmed purge. Keep the existing isolated Wasm runtime, quotas and C-SEC/Editor trust boundaries unchanged.

### Performance, bounded resources and diagnostics

No new runtime dependencies, scheduler, worker service or LLM inference. Keep one content command per plugin invocation, current-page selections of 1–100, one request in flight per bulk operation, existing plugin limits and existing site memory cap. Limit pending destructive plugin confirmations to one per actor/session/plugin/action, 32 globally per site, 120 seconds lifetime, at most 64 KiB retained per item (2 MiB total, plus small map overhead); retain only a typed command and bounded host-generated display metadata, not guest payloads, secrets, Wasm, database transactions or admission leases. Reject oversized or excess requests without canonical CMS mutations or lifecycle hooks; confirmation-capable actions cannot perform external HTTP. Invalidate on shutdown/restart, maintenance admission epoch change, session logout/revocation or expiry; prune expired and obsolete-epoch items before insertion/lookup. Revoked-session items that are not looked up may occupy a bounded slot until TTL but can never commit or disclose metadata. All confirmations reauthorize at commit.

Owner-approved quantitative acceptance gates (not benchmark results): on the same machine/build profile, identical deterministic 1k/10k/50k entry fixtures and role/filter scope specified by the canonical S04 workload below, compare 5 warmup and 30 measured list requests per case, and at least 30 measured repetitions for each 20/100-row bulk workload. Use median and p95, report spread and load; P1: active list/count p95 must be no more than max(1.25 times baseline p95, baseline p95 + 50 ms). P2: existing equivalent publish/draft batch p95 must be no more than max(1.25 times baseline, baseline + 1 s). P3: new trash/restore/taxonomy operations must not hold a SQLite writer across network/Wasm/human waits; p95 per-entry server mutation time, excluding bounded plugin execution, must be at most 500 ms on the 10k fixture and 2 s on 50k, no unhandled SQLITE_BUSY or timeout and no loss of committed rows. Report actual WAL high-water mark, peak RSS, backup bytes, retained count/age and hook queue/drop counts; preserve existing M8 memory safety checks and do not silently waive a regression. A budget miss blocks closure until optimized or explicitly accepted in a spec amendment. Match cohort, initial state, role, filter and operation; reset deterministic fixture for each bulk repetition and distinguish per-row server latency from whole-batch latency. Report Purge timing without inventing a separate threshold. These are engineering gates, not a measured SLA.

Diagnostics use existing local logging and bounded counters, with correlation IDs, operation and stable reason, actor/role, scope, expected/committed version, elapsed time and secondary outcomes. Never log content, credentials, raw confirmation tokens or private values. Existing async hook delivery remains best effort. Failure of post-commit projection/hook work must be reported separately from the durable mutation and must not cause a replay. Reconciliation re-reads authoritative state; a repair action may recompute current eligible projections through existing plugin enable/recompute flow without replaying the entry mutation.

### Upgrade and rollback

Migration is additive and old database rows remain active. Release only after S01+S02 pass together; do not expose partial recovery UI or new plugin capabilities. Upgrade from the exact previous executable/schema on an isolated populated fixture and prove that the old binary refuses the upgraded DB before serving any requests. SQLx compiled migration validation and existing restore ledger checks are the intended protection; if the negative test fails, do not activate the feature until a reviewed compatibility fence is implemented. No downgrade by dropping the lifecycle column, no mixed old/new processes on one site root. Existing pre-upgrade encrypted backup restores to a separate root under Safe Mode; post-upgrade writes require explicit reconciliation. No modification, stop, replacement or test use of the owner's site on port 18964.
