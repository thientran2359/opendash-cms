## 4. Shared package, ABI, permissions and lifecycle proposal

### 4.1 Identity and wire compatibility

Keep `api_version:1`, namespace `opendash_v1`, four existing host signatures, `plugin.wasm` entrypoint and existing manual input/output. Add explicit **`extension_contract:1` + `requires_host_contract`** to an extended manifest; loader must reject unsupported requirements before execution. Existing v1 packages without extension metadata use legacy behavior. An extended package must not claim it is safe on an old host that silently ignores extension fields: SDK/packaging and minimum-host version checks need a concrete compatibility test. Whether fail-closed needs a new manifest format discriminator is decision D01, not solved merely by adding JSON fields.

Proposed strict subdocuments: `declarations {content_types, taxonomy_eligibility, blocks, templates, settings, admin_screens}`, `capabilities`, `subscriptions`, `actions`. Unknown fields/ops, duplicates and unsupported versions in these documents reject; optional absence retains v1 defaults. Do not reinterpret existing `permissions.http` URLs as path scopes: they currently grant the entire matching origin. New structured network scopes get a distinct version/key and UI label.

Use existing ID validators; package ID is kebab, CPT/field keys stay SnakeKey, block IDs stay NamespacedBlockId. **Do not mechanically map kebab package IDs to SnakeKey owner IDs** or infer ownership from a prefix. Proposed logical identity is `(ResourceOwner::Plugin(plugin_id), resource_kind, canonical_key)` with canonical domain key uniqueness unchanged. Prefix convention helps authors but does not grant a claim; `post`, `page`, `core/*`, user/theme/other-plugin claims remain protected even when inactive/withdrawn.

All eight candidates keep the existing package ceilings initially: 5 MiB ZIP, 10 MiB decoded, 64 KiB manifest, 2 MiB Wasm, 10 flat entries. Recommend inline bounded declaration/template data in the versioned manifest for the first bridge, retaining the flat safe reader. Rich declarations may hit 64 KiB; reject with an explicit quota error rather than silently raising limits. Adding asset directories or larger manifests requires a separate reviewed package-path/quota delta and adversarial corpus. This is a deliberate authoring constraint to avoid importing theme ZIP v2 path semantics accidentally.

### 4.2 Canonical transaction and revision model

Propose additive immutable **plugin revision metadata/Wasm blobs in SQLite**, since plugin bytes already live there; no new filesystem publication protocol is needed for this initial flat package. Record plugin ID, SemVer, canonical digest over exact validated file names/bytes, contract version and provenance. Same ID/version/different digest is 409; identical digest is idempotent. Old `plugins` identity/enable row becomes pointer/generation authority; do not maintain two writable executable sources. Forward migration backfills an explicitly tagged digest from stored manifest/Wasm, never inventing an original ZIP checksum.

Install/update success continues to enable a valid package as in M2, but becomes **one all-or-nothing operation**: Admin/CSRF/Origin → bounded ZIP/ABI/schema/security validation → transaction/CAS of existing plugin generation → canonical domain compatibility and declaration sync → executable revision pointer + enabled + generation → commit. Rejecting any declaration preserves old pointer, enabled state, schema, values and layouts. Reinstall of the same digest is idempotent and does not reset values. Show permissions as information and automatically apply valid declared grants; no separate grant-approval checkbox/dialog. A normal explicit install/enable action is still required.

All proposed mutation DTOs use existing If-Match semantics (missing 428, malformed 400, stale 412); fresh creation uses an explicit create precondition to prevent concurrent duplicate replacement. Distinguish 409 identity/owner conflict, 422 incompatible/invalid domain declaration, 413 quota, 401/403 auth/permission. Exact install create-precondition/header compatibility and legacy client transition are D02.

Disable atomically sets enabled=false, increments generation and marks only that plugin's provider availability inactive. It does **not** withdraw declarations, delete schema, entries, settings, AST, menus, term links or plugin KV. Re-enable checks current revision/compatibility and restores availability only; it cannot bulk re-declare withdrawn resources. Update omission marks declared resources withdrawn independently. Missing/corrupt executable yields unavailable diagnostics and blocks code; retained valid schema remains usable. New content management never depends on executing guest code.

Running invocation leases bind `(plugin_id,revision_digest,generation,mode,actor,deadline)`. Parent validates these on IPC **and at commit**. Disable/update cancels affected workers; a write transaction serializes generation check with writes. If a write committed before disable acquired the serialization point, report committed success; otherwise stale generation prevents mutation. Do not claim disable retracts an already sent HTTP request. Recovery/Admin disable/list routes must not need a plugin permit or guest execution.

## 5. P08 — CPT and field bridge (deep proposal)

**Recommended seam:** extract owner-neutral transaction-aware CNT registration/evolution in `storage/content.rs` with explicit owner and provider state. Keep `sync_theme_declarations_in_tx` as the theme adapter that alone performs theme-switch deactivation; plugin adapter syncs only one `Plugin(id)`. Names such as `sync_provider_declarations_in_tx` here describe **future work**, not existing APIs. Keep validation types in core; no SQL/I/O there.

Manifest CPTs use canonical `ContentTypeDefinition` field kinds/limits. First version supports fields within a plugin-owned CPT; attaching plugin fields to Core post/page or another provider's CPT is **BLOCKED D03**, pending field-level ownership, conflict and migration semantics. Do not silently omit the PRD fields capability: nested custom fields satisfy the first bridge, and independent attachment must be expressly decided before scope is finalized.

Compatibility policy starts from the actual conservative `check_content_type_compatibility`: label/help changes and optional additions allowed; type change and required tightening rejected; removal/rename and select-option removal rejected when entries exist; adding a required field rejected even on an empty type by current code. Do not loosen this to “scan currently used values” without an explicit domain decision. New plugin-owned CPT may declare required fields at first creation. Old entries/values, media refs and schema remain authoritative. Omission of an entire CPT withdraws it but keeps its last valid complete schema. A future destructive migration must be explicit, separately reviewed and backed by restore evidence; no guest migration SQL.

Transaction success publishes all CPT/field/eligibility claims and plugin revision together; failure leaves no partial reservation. Reload catalog from committed DB. Re-declaration by the same owner must pass compatibility and preserve IDs/content. Other-owner keys remain reserved forever until a separately authorized data operation; inactive owner never means free namespace. Registration race with theme activation/user schema create must have one winner under DB uniqueness/serialized write, not preflight-only checks.

Acceptance / negatives:

- Install plugin A with a required and optional field, edit entries as Admin and Editor; disable/restart and edit again without guest code. Re-enable/reinstall compatible A2 preserves IDs, values, terms, media and public publication policy.
- Withdraw/re-declare CPT; update adds optional field/select option; label update; retained data stays editable. Reject wrong type, invalid key, duplicate fields, forbidden built-in claim, user/theme/B owner collision including inactive/withdrawn, required tightening, data-invalidating removal/rename and bad taxonomy binding.
- Inject failure at second declaration, pointer CAS, DB busy/commit and cancellation; no partial schema/enable/pointer change. Race schema evolution versus content Save; final stored record validates against committed schema, with explicit conflict rather than dropped values.
- Migration from pre-M6 plugin and theme schemas retains owners/declaration axes; restart cannot synthesize owner from namespace. Snapshot restore uses matching old binary, not reverse SQL.

## 6. P01 — content events, actions and server APIs (deep proposal)

### 6.1 Two phases, no detached writes

Recommend **before-save validator/veto**, rather than arbitrary content transformations or arbitrary DB access while holding SQLite's write lock. Alternatives: hold write transaction over worker/network calls (reject lock/starvation/deadlock risk); let each hook commit independently (reject partial content/KV success); pure bounded validation before transaction followed by transactional revalidation (recommended, but requires an explicit read-set protocol).

Create/update use case flow: guard actor and input → load schema/entry/eligible provider snapshot and version tokens → dispatch ordered validators on bounded immutable candidate → collect allow/veto → enter canonical write transaction → recheck session/role, entry CAS, schema/declaration/provider generation tokens, media existence and term validity/eligibility → canonical write → commit → restricted after-save notification → return committed result. Stale read-set returns 412 and **does not automatically rerun** validators. For creation, include schema generation and slug uniqueness; never expose a noncommitted database ID to the validator as final identity.

Before-save envelope retains `HookEnvelope` with a versioned payload: operation=create/update, type key, optional stable entry ID, expected entry version, schema token, candidate values/title/slug/term IDs, actor role/ID only if required, correlation ID and deadline. Only subscriptions with explicit content-read capability for that type receive candidate/private fields; zero session/token/password/absolute paths. Candidate transfer is capped by existing input/output bounds. Missing capability must reject subscription installation, not silently skip an expected validator.

Before handler output is a strict tagged `allow` or `veto {code,field_errors}`; veto diagnostics are bounded escaped plain text. First veto ends validation deterministically. Invalid output, trap, timeout, unavailable required provider, discovery failure or exhausted handler budget **fails that Save closed** with no domain/KV writes; Admin retains input and shows diagnostics. Disabled plugin is absent from the admission snapshot; a required admitted plugin becoming disabled mid-phase invalidates the snapshot. Explicit Admin disable restores ability to save on a new attempt; unrelated content types and recovery routes remain usable. No hidden fail-open flag.

Before mode has **no HTTP, KV writes, content writes, nested actions or recursive dispatch**, even if the normal manifest grants them. Read needs come from the immutable envelope/read snapshot, not a second pool acquisition under a locked transaction. Mode restriction is enforced in the parent and worker, not a guest promise. It avoids staging KV across independent workers/commits. Longer term transformations would require a separately versioned ordered-patch/revalidation contract.

After-save occurs only after successful durable content commit, receives committed ID/version and restricted payload, cannot veto or rewrite saved content. In the new ContentAfterSave mode, allow bounded read/diagnostic output only; no staged KV/content writes or HTTP. Handler failures are reported/logged but must not change successful Save to timeout/error. **No exactly-once/durable-delivery promise**: process death after commit may lose notification. Durable integration/outbox is a future explicit decision, not an invisible queue. Existing PageAfterSave v1 behavior and KV permissions stay compatibility-tested; do not accidentally claim that it is globally side-effect-free.

Ordering stays `(priority,id)`, sequential, unique stable handler IDs; plugin default priority 100. Keep 32 handlers and 5s admission ceiling, but add a strict total phase deadline so 32 × 5s cannot block one Save. Proposed before total 5s, after total 5s including worker cleanup; per-handler remaining budget must propagate into runtime instead of applying an unsafe outer timeout around commit. Core callbacks remain trusted/cooperative, 250ms. Whether these budgets are usable needs feasibility/latency evidence (D04); they are design ceilings, not measured performance.

### 6.2 Explicit actions / host APIs

Server API calls go through `host_call` JSON with versioned named ops and structured errors, never raw SQL/HTTP loopback to Admin routes. Initial proposed operations: content read/list with type scope and publication/actor filter; a standalone action may submit a bounded **single content command** using canonical Save orchestration and expected version. Content write capability is intersected with initiating actor's current RBAC; plugin code is not automatically Admin. No arbitrary user/settings/role mutation permission; default deny unknown ops. A plugin cannot invoke itself recursively through the content hooks triggered by its own action; reject nested dispatch deterministically rather than silently omit validation.

Action registration is a bounded ID + input schema + required role/capabilities + timeout + public-effect declaration. Only authenticated CMS-dispatched actions exist in V1; no arbitrary public plugin route, timer or scheduler. One action request has one visible commit outcome; guest-computed output and permitted writes must validate before commit. Until atomic content-command + KV policy and nested hook behavior are resolved, **mixed KV/content writes are rejected**, not two independent commits. HTTP actions cannot promise DB rollback of external effects; no automatic retry, and use an explicit action request identity for safe result retrieval after disconnect. No new idempotency ledger is implied to exist today.

Scope choice: ContentBefore/AfterSave cover create/update, including edits to published content and draft Saves; Publish/Unpublish and Delete remain distinct operations with **no Save hooks** in this proposal. D05 must confirm that exclusion and action eligibility so implementation does not invent events. Preview must not invoke write-capable actions or publish anything.

Acceptance / negatives: deterministic ordering/ties, veto first/middle, malformed response, 32/33 handlers, total-budget exhaustion, DNS/HTTP denied in before/after, actor revoked while validating, stale schema/media/term/CAS, duplicate slug, client disconnect before/at/after commit, disable/update racing worker completion, corrupted manifest and nested action. Validate zero late writes by waiting past the former deadline and reopening DB; a success after commit remains success. Test draft nonpublic/published Save public and Builder regression separately. Failed after notification must leave committed success and next handler/recovery behavior deterministic.

## 7. P02 — external calls and capability enforcement

Keep existing v1 origin grants as explicitly labelled compatibility semantics. Proposed v2 network scope is normalized exact scheme/host/effective port + method allowlist + optional **path-segment prefix**. No substring hostname/path comparison or wildcard private-network grant. Reject credentials/fragments, malformed encodings and ambiguous normalized paths. HTTPS by default for new declarations; retaining explicit legacy HTTP needs compatibility policy. Path scope alone cannot prevent an allowed service from forwarding data, so do not describe it as a secret-exfiltration proof.

Validate all DNS answers against a centralized public-address policy, including IPv4-mapped IPv6, special-use ranges and mixed public/private answers; pin checked addresses for the actual connection/SNI host. Forbid localhost/private/link-local/metadata/multicast/unspecified and environmental proxy. Redirects remain disabled; return a bounded status/diagnostic without following Location. Reject guest `Host`, proxy and hop-by-hop headers, CRLF, and URL credentials; do not log Authorization/cookie/request body/query secrets.
