The hypothesis provides enough objective/context to proceed to refinement. Four findings deserve priority:

1. **Major — Contrarian / YAGNI & Code Minimization: establish the smallest migration that solves the problem.**
   The hypothesis combines adopting official review skills, replacing lifecycle terminology, reconciling authority, modifying dispatch, reorganizing documentation and conducting a pilot (`2026-11-20-egm-migration-concepts.md:8,16–24`). These changes have different risks and need not ship together. Actual source already mixes the new mandatory owner-approval sequence (`AGENTS.md:5,13,25`) with retained delegated authority: ADR-0010 allows Atlas technical decisions and autonomous implementer delivery (`docs/decisions/ADR-0010-agent-project-and-merge-authority.md:75–85`).
   **Alternative:** compare (a) official EGM as a design/review layer over current operational gates, (b) staged lifecycle migration, and (c) comprehensive replacement. Prefer a bounded pilot and explicit vocabulary/authority mapping first unless the broader replacement has a demonstrated benefit. Do not make the owner a new default technical approval bottleneck. Preserve product/release authority and every security/data/native/human gate.

2. **Major — Contrarian / YAGNI & Code Minimization: task identity need not change because document structure changes.**
   The generator already accepts an explicit task ID but defaults new designs to `EGM-{stem}` (`.agents/scripts/prepare-github-issue.py:207–221`). Existing transport rejects that default: `TASK_RE` accepts only milestone IDs (`.agents/scripts/cos_dispatch.py:33`), and send/resume/status all validate it (`612,797,882`). Task IDs also participate in receipt hashes and locks (`438,560,677–678` from search).
   **Alternative:** first evaluate retaining assigned stable milestone task IDs for EGM-backed Issues. This preserves legacy receipts and reduces migration surface. If new identifiers are a real requirement, reuse the existing generator/adapter paths with one compatible identity contract and tests across generation, send, status, resume, ACK and locks. Do not rename existing tasks or treat a new SHA/ID as permission to redeliver. The hypothesis correctly warns against a regex-only fix; it should explicitly compare the no-identity-change option.

3. **Major — Contrarian / YAGNI & Code Minimization: strengthen existing validators instead of building a new approval system.**
   The hypothesis asks for meaningful plans and provenance (`concepts:21–22`). Existing generator checks `Approved` metadata, nonempty top-level sections and the presence of two subsection headings (`.agents/scripts/prepare-github-issue.py:187–202`), but those checks do not establish nonempty target/verification contents or approval provenance. Existing tests cover missing headings and selected placeholders (`.agents/scripts/test_prepare_github_issue.py:214–229`). Separately, `claims_verified` explicitly checks only bold status text (`cms/scripts/check-plans.py:62–65`).
   **Alternative:** extend these existing parsers and fixtures with empty-section, formatting-independent status and misleading-content negatives. Keep approval provenance a bounded Issue/PR/review evidence obligation, using existing immutable `source_sha` and reviewed-head records, rather than inventing a parallel workflow database or treating Markdown as an authority token. Mechanical validation cannot prove engineering adequacy or real verification.

4. **Major — Contrarian / YAGNI & Code Minimization: define a low-cost, falsifiable pilot before repository-wide adoption.**
   The proposal says “pilot a real workflow” and record elapsed time (`concepts:24`), but lacks an exit condition. Actual source mandates Rust formatting/build/release tests even after documentation edits (`AGENTS.md:61–71`); the context loader repeats full-suite requirements for every verification plan (`.agents/skills/opendash-elephant/SKILL.md:39–47`). This creates recurring cost unrelated to workflow-document changes.
   **Alternative:** one coordinator-host pilot on an eligible, explicitly owned process task: actual upstream personas/standards read, useful findings, resolved design, offline Issue generation and adapter contract tests without live dispatch unless separately authorized. Select checks by changed behavior; reuse existing generator/dispatch/resume fixtures. Record time, unexpected gate conflicts and retained requirements, then decide whether expansion is worthwhile. If no safe eligible task exists, report a limited dry-run rather than manufacturing eligibility. The pilot cannot establish macOS Beta, public-release readiness or cleared F08/F09 holds; ADR-0010:52–66 expressly preserves those obligations.
